# Phase 6.04 -- Worker Protocol & Commit-Budget Plan

## Purpose

Introduce a host <-> worker protocol that allows parallel planning and computation
while preserving all locked Phase-6 invariants:

- One commit per tick
- No mid-tick visibility
- Deterministic outcomes
- Host-controlled commit / rollback / fallback
- DOM mutations only during commit

This phase explicitly does not parallelize JS execution or DOM access.
All parallelism occurs behind the commit boundary.

---

## Non-Goals

- Parallel DOM mutation
- Weakening mutation guards
- Changing JS execution semantics
- Replacing framework logic (React, etc.)

---

## Architecture Overview

```
┌──────────────┐          postMessage           ┌──────────────┐
│  Host (UI)   │  ─────────────────────────▶  │   Worker     │
│              │                                │ (Planner)   │
│  - tick loop │  ◀─────────────────────────   │             │
│  - commit    │        PatchBatch / Abort      │ - compute   │
│  - rollback  │                                │ - diff      │
└──────────────┘                                └──────────────┘
```

The host remains authoritative over:
- when a tick begins
- when (or whether) a commit occurs
- fallback behavior

The worker is authoritative over:
- state evolution
- diff / patch planning
- expensive compute

---

## Message Protocol

### Host -> Worker

#### `BEGIN_TICK`
```ts
{
  type: "BEGIN_TICK",
  tickId: number,
  inputs: EventEnvelope[],
  budget: CommitBudget
}
```

- Sent once per tick
- `inputs` are immutable snapshots of host-observed events
- `budget` defines soft limits (see below)

---

### Worker -> Host

#### `PATCH_BATCH`

```ts
{
  type: "PATCH_BATCH",
  tickId: number,
  metaKind: "commit",
  ops: PatchOp[],
  stats: WorkerStats
}
```

- Returned at most once per tick
- Contains a fully prepared patch list
- Host applies only if within budget

#### `ABORT`

```ts
{
  type: "ABORT",
  tickId: number,
  reason: string,
  stats?: WorkerStats
}
```

- Worker detected it cannot safely produce a patch
- Host performs rollback or fallback

---

## Commit Budget

Budgets are enforcement thresholds, not promises.

```ts
type CommitBudget = {
  maxOps: number         // maximum PatchOps
  maxPatchBytes: number  // serialized size
  maxWorkerMs: number    // soft compute cap
}
```

Rules:

- Worker may exceed budget internally
- Host is the final arbiter
- Over-budget patches are rejected deterministically

---

## Host Commit Decision Ladder

1. Validate `tickId`
2. Validate deterministic fingerprint (if present)
3. Check commit budget
4. If pass -> `commit()`
5. If fail -> `rollback()` or `fallback()`

Fallback options:

- retry serial path
- drop to observation-only mode
- reset worker state

No partial commits are allowed.

---

## Determinism & Replay

- Worker state evolution must be pure w.r.t inputs
- Host may request replay using recorded inputs
- PatchBatch must be byte-stable across replays

---

## Telemetry Hooks

WorkerStats (example):

```ts
{
  worker_ms: number,
  planned_ops: number,
  skipped_ops: number,
  patch_bytes: number
}
```

Host records:

- accept/reject reason
- fallback path taken
- tick duration

---

## Rollout Strategy

Phase 6.04 introduces the protocol behind a feature flag:

- Default: worker disabled
- Flag on: worker planning active, host commit enforced
- Any violation auto-disables flag

---

## Success Criteria

- No behavior change with flag enabled
- Deterministic replay equivalence
- Host never blocks on worker
- Observable reduction in main-thread compute when worker enabled

---

## Exit Criteria

Proceed to Phase 6.05 only after:

- At least one real subsystem uses worker planning
- Telemetry shows bounded commit behavior
- No invariant regressions across replay tests
